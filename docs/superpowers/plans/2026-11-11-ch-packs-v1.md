# ch-packs v1 Implementation Plan

> **Design document.** It describes what is planned and decided, not what exists; what is built is stated in each package repository's README. Numbers in examples are illustrative, dates are estimates that move, and nothing here is a promise to a user.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pack 1 (CI failure triage) installable by a stranger in Claude Code and Cursor within five minutes, with the receipt and the layer-1 usage report, built on the access/step/scenario layering so pack 2 reuses the steps.

**Architecture:** One repository per package under `mchen6` since the split (see Repositories); before it, one repository with npm workspaces. Pure JavaScript, no runtime dependency outside Node's built-ins except the countinghouse runtime itself. Step modules are pure functions wrapped as countinghouse modules and unit-tested by calling their handlers directly. The access module speaks to GitHub's MCP server through the runtime's RC1 remote declaration. The scenario module composes them with `ctx.call`. The launcher (`ch-local`) installs pinned tarballs, writes client configuration, starts the runtime in local mode and reads the usage files for the report.

**Tech Stack:** Node >= 22.16 (floor shim pending in countinghouse; until it lands, develop on 24), `node:test` + `node:assert`, countinghouse 8.0 (git dependency on `mchen6/countinghouse#master` as devDependency until an 8.0 is on npm), GitHub Actions on `ubuntu-latest`, `macos-latest`, `windows-latest`.

**Spec:** `docs/superpowers/specs/2026-11-11-client-packs-design.md` (approved 2026-11-11). Sections are cited as "spec §N".

## Global Constraints

- Every package lives under an owned npm scope (Matt, 2026-11-11 10:38; named `@countinghouse` on 2026-11-11 ~17:00; written as `@countinghouse` in each package repository's `package.json`; the shared constant `scripts/lib/scope.js` went with the split) and keeps the `ch-` prefix inside it so names stay recognisable (tech's call): `@countinghouse/ch-local`, `@countinghouse/ch-access-github`, `@countinghouse/ch-step-redact`, `@countinghouse/ch-step-log-clean`, `@countinghouse/ch-step-error-patterns`, `@countinghouse/ch-step-failure-signature`, `@countinghouse/ch-step-dedupe`, `@countinghouse/ch-step-owner-hint`, `@countinghouse/ch-step-report`, `@countinghouse/ch-pack-ci-failure-triage`, `@countinghouse/ch-report`. Module `friendlyName`s and `calls` addresses use the bare `ch-…` name. Until the scope exists, packages are installed from tarballs only.
- Pack order after pack 1: 2, 4, 3, 5, 6, 7, 8 (Matt, 10:38).
- Upgrade: easy, never silent; automatic upgrade is an opt-in setting, off by default (Matt, 10:38).
- The report (the runtime's `countinghouse_usage_report` tool and its `countinghouse-usage` command line and export, LM1 spec §5; Matt, 2026-11-11) carries an approximate token column beside the exact bytes and lines, labelled as an estimate and naming its method; the receipt stays bytes and lines (Matt, 10:37).
- Pure JavaScript: no native module, no shell script, every `bin` a `.js` file, no symlinks, paths through `path` and `os.homedir()`, atomic writes by temp-file-and-rename, env read case-insensitively on Windows, `child.kill()` without signal names, stdio in binary mode (spec §2).
- No telemetry, no phone-home, no update check; the only outbound calls are the access module's calls to declared servers, plus `install`/`upgrade` when the user runs them (spec §2, §11).
- No key, token or secret in any log line, error text, receipt, report, cache or module input/output; caches hold fingerprints and hashes (spec §11).
- Only scenario modules carry `"countinghouse": {"role": "scenario"}`; access and step modules carry `"role": "part"` and are never listed (spec §4).
- The receipt is attached by the runtime, not by any module, from what the runtime can count: lines and bytes of the text content of every server result, the number of server calls, and the lines and bytes of the tool result after redaction. It reads "read 48,210 lines (3.1 MB) in 14 calls to github; 35 lines (2.4 KB) reached the model." A "line" is a newline-separated line of a result's text content, JSON results included; the scenario's `coverage` block carries the pack-specific units (runs, logs). Never the word "saved" (spec §6, amended 2026-11-11).
- Usage records: one append-only JSONL file per launcher process at `~/.countinghouse/usage/<YYYY-MM-DD>/<pid>-<startMs>.jsonl`, one record per call: `{t, call, pack, tool, server, bytesIn, linesIn, bytesOut, linesOut, ms, outcome, credential}` where `credential` is a variable name and `call` ties a tool call's server records to its result (no session field: MCP is stateless; the file names the process) (spec §6).
- Every module passes `npx countinghouse-validate <dir>` with exit 0 and runs under `--moduleSandbox enforce`.
- Handler contract (countinghouse): `module.exports = async (input, ctx) => ({output})`; faults are `throw new DeviceError(code, message)`; inner hops are `await ctx.call('<module>/<service>.<action>', input, {detail: true})` returning `{data: {output}, platformMetering}`; a module's private directory is `/data`.
- Commits: one task per PR on a branch `task-N-<slug>`; `npm test` green on all three OS before the PR is marked ready; the reviewer session merges.
- Acceptance before publication runs from local tarballs: `ch-local install --from <dir>` (spec goals).

## Review Focus

1. A GitHub Actions log with Windows line endings (`\r\n`) and a UTF-8 BOM: `ch-step-log-clean` must strip both and still find `##[group]` markers (Task 3 test `cleans CRLF and BOM logs`).
2. A job log that has expired (GitHub answers 410 or 404 for logs older than the retention period): `ch-access-github.jobLog` returns `{expired: true}` rather than throwing, and the scenario's coverage block counts it (Task 8 test `expired logs are counted, not fatal`; Task 9 test `coverage reports expired logs`).
3. A repository with no failed run in the window: the scenario answers `{status: 'no-failed-run'}` with the last successful run, never an error (Task 9 test `no failed run in the window`).
4. A log line that holds a GitHub token (`ghp_…`, `github_pat_…`) or a bearer header in the error lines: `ch-step-redact` replaces it before it can reach the result (Task 2 test `github tokens and bearer headers are masked`).
5. Two launcher processes starting at the same millisecond on the same machine: their usage files must not collide (`<pid>-<startMs>` differs by pid) and both must land in the one per-user usage directory (Task 13's two-launcher check). There is no auth file to race on: the launcher is the single-identity profile, whose key lives in memory (reviewer, 2026-11-12).
6. A secret that spans several log lines (a private key block) where error extraction keeps only part of it: the chain rule (reviewer, 2026-11-11, from Task 9's review) is that **a step's lines are redacted whole before any extraction picks from them, and the picked lines again before they leave**. A real-length key's body otherwise reaches `errors` when error-patterns keeps the block's tail without its BEGIN line. Task 9 test `a private key block in the error lines is masked whole`, with a key generated at test time. Measured cost, per log: the 60,000-line, 5 MB+ log goes through the whole chain in about 610 ms in-process with whole-step redaction (about 350 ms without), within the 3 s budget.

Runtime interfaces this plan consumes, to be aligned with the countinghouse specs when they land (the owning implementer is named; until then the values below are this plan's assumption and the task that first needs them stops and asks):

- RC1-min (A): `package.json` `countinghouse.remotes: [{name, transport: 'streamable-http', url, headers: {<static, non-secret name>: <value>}, credential: {env: 'NAME', fallbackEnv: 'NAME', header: 'Authorization', scheme: 'Bearer'}}]` (`headers` and `fallbackEnv`: reviewer, 2026-11-11); `ctx.call('remote:<name>/<tool>', args)` resolves with the raw MCP `CallToolResult` as the server sent it, `{content, isError?, structuredContent?}`, nothing parsed and nothing hidden; the runtime only counts bytes and lines on the way through, and a transport or protocol failure (unreachable, 401, malformed JSON-RPC) is a runtime error with a runtime code (reviewer, 2026-11-11; ch-access-github's `lib/remote.js` relies on it); tools/list recorded at load.
- LM1 (B, spec: countinghouse `docs/superpowers/specs/2026-11-11-local-mode-design.md`): `--store local` replaces Redis with a file-backed local store (metering, `ctx.redis`, an in-process job runner); `--stdio` serves MCP over stdio; `countinghouse.role` `scenario|part`; `--loadModule <scenario dir>` loads the scenario and its `calls` targets from node_modules, parts unlisted; `--usageDir` usage files as in Global Constraints; the receipt attached to scenario results.
- Floor shim (B, spec: countinghouse `docs/superpowers/specs/2026-11-11-node-floor-shim-design.md`): Node >= 22.16.
- R2-1's module-facing part (A, after RC1-min and the floor shim): no raw key reaches a module. The first public installable waits for it (Matt, 2026-11-12), so Task 11's `start`, Task 13 and Task 14 stop on it.
