# ch-packs v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pack 1 (CI failure triage) installable by a stranger in Claude Code and Cursor within five minutes, with the receipt and the layer-1 usage report, built on the access/step/scenario layering so pack 2 reuses the steps.

**Architecture:** One repository, npm workspaces, pure JavaScript, no runtime dependency outside Node's built-ins except the countinghouse runtime itself. Step modules are pure functions wrapped as countinghouse modules and unit-tested by calling their handlers directly. The access module speaks to GitHub's MCP server through the runtime's RC1 remote declaration. The scenario module composes them with `ctx.call`. The launcher (`ch-local`) installs pinned tarballs, writes client configuration, starts the runtime in local mode and reads the usage files for the report.

**Tech Stack:** Node >= 22.16 (floor shim pending in countinghouse; until it lands, develop on 24), `node:test` + `node:assert`, countinghouse 7.x (git dependency on `mchen6/countinghouse#master` as devDependency until a 7.x is on npm), GitHub Actions on `ubuntu-latest`, `macos-latest`, `windows-latest`.

**Spec:** `docs/superpowers/specs/2026-11-11-client-packs-design.md` (approved 2026-11-11). Sections are cited as "spec §N".

## Global Constraints

- Every package lives under an owned npm scope (Matt, 2026-11-11 10:38; the scope's name is not chosen yet, written `@SCOPE` below and in code as one constant) and keeps the `ch-` prefix inside it so names stay recognisable (tech's call): `@SCOPE/ch-local`, `@SCOPE/ch-access-github`, `@SCOPE/ch-step-redact`, `@SCOPE/ch-step-log-clean`, `@SCOPE/ch-step-error-patterns`, `@SCOPE/ch-step-failure-signature`, `@SCOPE/ch-step-dedupe`, `@SCOPE/ch-step-owner-hint`, `@SCOPE/ch-step-report`, `@SCOPE/ch-pack-ci-failure-triage`, `@SCOPE/ch-report`. Module `friendlyName`s and `calls` addresses use the bare `ch-…` name. Until the scope exists, packages are installed from tarballs only.
- Pack order after pack 1: 2, 4, 3, 5, 6, 7, 8 (Matt, 10:38).
- Upgrade: easy, never silent; automatic upgrade is an opt-in setting, off by default (Matt, 10:38).
- The report (command line, export, callable tool) carries an approximate token column beside the exact bytes and lines, labelled as an estimate and naming its method; the receipt stays bytes and lines (Matt, 10:37).
- Pure JavaScript: no native module, no shell script, every `bin` a `.js` file, no symlinks, paths through `path` and `os.homedir()`, atomic writes by temp-file-and-rename, env read case-insensitively on Windows, `child.kill()` without signal names, stdio in binary mode (spec §2).
- No telemetry, no phone-home, no update check; the only outbound calls are the access module's calls to declared servers, plus `install`/`upgrade` when the user runs them (spec §2, §11).
- No key, token or secret in any log line, error text, receipt, report, cache or module input/output; caches hold fingerprints and hashes (spec §11).
- Only scenario modules carry `"countinghouse": {"role": "scenario"}`; access and step modules carry `"role": "part"` and are never listed (spec §4).
- The receipt is attached by the runtime, not by any module, from what the runtime can count: lines and bytes of the text content of every server result, the number of server calls, and the lines and bytes of the tool result after redaction. It reads "read 48,210 lines (3.1 MB) in 14 calls to github; 35 lines (2.4 KB) reached the model." A "line" is a newline-separated line of a result's text content, JSON results included; the scenario's `coverage` block carries the pack-specific units (runs, logs). Never the word "saved" (spec §6, amended 2026-11-11).
- Usage records: one append-only JSONL file per launcher process at `~/.countinghouse/usage/<YYYY-MM-DD>/<pid>-<startMs>.jsonl`, one record per call: `{t, call, pack, tool, server, bytesIn, linesIn, bytesOut, linesOut, ms, outcome, credential}` where `credential` is a variable name and `call` ties a tool call's server records to its result (no session field: MCP is stateless; the file names the process) (spec §6).
- Every module passes `npx countinghouse-validate <dir>` with exit 0 and runs under `--moduleSandbox enforce`.
- Handler contract (countinghouse): `module.exports = async (input, ctx) => ({output})`; faults are `throw new DeviceError(code, message)`; inner hops are `await ctx.call('<module>/<service>.<action>', input, {detail: true})` returning `{data: {output}, platformMetering}`; a module's private directory is `/data`.
- Commits: one task per PR on a branch `task-N-<slug>`; `npm test` green on all three OS before the PR is marked ready; the reviewer session merges.
- Acceptance before publication runs from local tarballs: `ch-local install --from <dir>` (spec goals).

## Review Focus

1. A GitHub Actions log with Windows line endings (`\r\n`) and a UTF-8 BOM: `ch-step-log-clean` must strip both and still find `##[group]` markers (Task 3 test `cleans CRLF and BOM logs`).
2. A job log that has expired (GitHub answers 410 or 404 for logs older than the retention period): `ch-access-github.jobLog` returns `{expired: true}` rather than throwing, and the scenario's coverage block counts it (Task 8 test `expired logs are counted, not fatal`; Task 9 test `coverage reports expired logs`).
3. A repository with no failed run in the window: the scenario answers `{status: 'no-failed-run'}` with the last successful run, never an error (Task 9 test `no failed run in the window`).
4. A log line that holds a GitHub token (`ghp_…`, `github_pat_…`) or a bearer header in the error lines: `ch-step-redact` replaces it before it can reach the result (Task 2 test `github tokens and bearer headers are masked`).
5. Two launcher processes starting at the same millisecond on the same machine: their usage files must not collide (`<pid>-<startMs>` differs by pid) and the first-start creation of `auth.json` must not race (exclusive create, the loser reads) (Task 11 test `two launchers do not clobber auth.json`).
